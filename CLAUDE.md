## Project Overview

**APIC_A** is a tapeout-oriented Deep Learning Accelerator (DLA) for running a quantized MNIST GAN generator on a systolic array, backed by physical GF180MCU SRAM macros. The project covers HW/SW co-design: INT8 quantization of PyTorch checkpoints, structural synthesizable Verilog RTL, and OpenLane/LibreLane physical flow.

## Architecture

### Synthesis Boundary

`dla_engine_top` (and its sub-modules below) is the **tapeout target**. `g300_pipeline_top`, the testbenches, and all Python scripts are the verification harness — not taped out.

### RTL Module Hierarchy

```
dla_engine_top.v          ← TAPEOUT BOUNDARY
  ├── dla_controller.v    ← 4-state FSM: IDLE→CLEAR→COMPUTE→DONE
  ├── dla_pe_array.v      ← N×N grid of PEs
  │     └── dla_pe.v      ← INT8 multiply + 24-bit accumulate
  ├── dla_a_buffer_bank.v ← A matrix buffer (USE_SRAM=1 → 4 SRAM macros)
  ├── dla_b_buffer_bank.v ← B matrix buffer (USE_SRAM=1 → 4 SRAM macros)
  ├── dla_c_buffer_bank.v ← C result buffer (USE_SRAM=1 → 3 SRAM macros)
  └── gf180_sram_1rw_256x8.v ← SRAM wrapper with `ifdef SYNTHESIS guard

g300_pipeline_top.v       ← Sim-only GAN orchestrator (drives dla_engine_top)
```

### Key Design Details

**SRAM behavioral vs. synthesis switching:** `gf180_sram_1rw_256x8.v` uses `` `ifdef SYNTHESIS `` to switch between a behavioral model (for Icarus simulation) and a `(* blackbox *)` stub (for synthesis). Without `-DSYNTHESIS`, Yosys would synthesize ~22k flip-flops instead of placing the hard macro.

**SRAM latency alignment:** SRAM reads have 1-cycle registered latency. `dla_engine_top` pipelines `en_pe`, `done`, and `busy` by one cycle when `SRAM_LATENCY=1` to keep the PE enable aligned with valid SRAM read data.

**Buffer configuration (current 11-macro variant):** A, B, and C buffers all use `USE_SRAM(1)`, so **11 SRAM macros** appear in layout (A=4 `GEN_A_ROWS`, B=4 `GEN_B_COLS`, C=3 `u_sram0..2`). The 3-macro variant (A/B as `USE_SRAM(0)` register memory, only C in SRAM) is the fallback for a faster/smaller run; to go back, set A/B `USE_SRAM(0)` in `dla_engine_top.v` and shrink `DIE_AREA` to `[0,0,1250,900]` (+ trim `MACROS.instances` to the 3 C entries).

**GAN tiling:** `g300_pipeline_top` tiles each dense layer (64→256→256→784, ReLU/ReLU/Tanh) onto the 4×4 DLA. Each `start` computes 4 output neurons; requantization constants and a Q20 fixed-point tanh LUT handle post-processing. Constants are generated by `gen_g300_int8_assets.py` and emitted as `rtl/g300_quant_params.vh`.

### LibreLane bring-up notes (config fixes & rationale)

These are the changes that took the flow from failing-at-lint to a clean GDS
(Magic DRC = 0, Netgen LVS = 0). Each was a real blocker, in flow order:

1. **SRAM blackbox power pins** (`rtl/gf180_sram_1rw_256x8.v`): do **not** tie the
   macro's `inout` VDD/VSS to constants (`.VDD(1'b1)`/`.VSS(1'b0)`) — Verilator
   lints with `+USE_POWER_PINS` and rejects it (`PORTSHORT`/`UNSUPPORTED`). Leave
   macro power unconnected in RTL; the PDN connects it physically via
   `PDN_MACRO_CONNECTIONS` from the LEF (same as `Friend_reference/sram_rtl_friend.v`).
2. **Macro placement / registration**: use the modern `MACROS:` config variable
   (gds/lef/lib + `instances:` with `location`/`orientation`), not the deprecated
   `EXTRA_LEFS`/`EXTRA_GDS_FILES`/`EXTRA_LIBS` + `MACRO_PLACEMENT_CFG`. The Classic
   flow does not auto-place hard macros — without explicit placement, PDN aborts
   with `[PDN-0235] unplaced macros`.
3. **PDN macro connect** (`librelane/pdn_cfg.tcl`, set via `PDN_CFG`): the gf180 SRAM
   power pins top out at **Metal3**, so the stock macro grid connect (Metal4↔Metal5)
   makes no vias → `[PDN-0232]`/`[PDN-0233]`. Fix: `add_pdn_connect -grid macro
   -layers "Metal3 $::env(PDN_VERTICAL_LAYER)"`. (pdn_cfg.tcl is a copy of the proven
   chipathon padring script with just that one line changed.)
4. **Die size / utilisation**: macros + std cells too dense → `[DPL-0036]` detailed
   placement fails; target ~45% util. **11-macro (current):** 11 macros (~745k µm²) +
   ~260k µm² std cells on `DIE_AREA: [0,0,1600,1500]` ≈ 43–48% util; macros on a 4×3
   grid (x=90/460/830/1200, y=150/640/1130, ~69 µm H channels / ~265 µm V channels).
   **3-macro fallback:** `DIE_AREA: [0,0,1250,900]` (~46%), macros x=100/475/850, y=337.
5. **Cell padding**: gf180 default `GPL_CELL_PADDING` is 0; antenna diodes get no pin
   access (`[DRT-0073]`). Set `GPL_CELL_PADDING: 1`, `DPL_CELL_PADDING: 2`.
6. **Routing layers**: `RT_MAX_LAYER: Metal5` (was Metal4) so the clock tree can
   layer-hop to break antennas. Metal5 is free (PDN is Metal4-only, `PDN_MULTILAYER:
   false`).
7. **Antenna repair**: violations are on datapath/fanout nets (Metal2/3), NOT the
   clock tree. Naively re-enabling in-router diode repair crashes with `[DRT-0073]
   No access point` (it inserts diodes it can't route to). Fix = attack antennas
   PRE-route: `RUN_HEURISTIC_DIODE_INSERTION: true` (diodes placed by GPL, always have
   access) + `GRT_ANTENNA_REPAIR_MARGIN: 25`. On the 11-macro route this drove the
   post-GRT check to **0 net/0 pin**; after detailed routing ONE mild Metal2 datapath
   net remains (~1.2×). **Keep `DRT_ANTENNA_REPAIR_ITERS: 0`.** Re-enabling the
   in-detailed-router repair (ANY `ITERS≥1`, incl. `DRT_ANTENNA_REPAIR_JUMPER_ONLY:
   true`) crashes with `[DRT-0073] No access point`: `ITERS≥1` triggers a verification
   re-route whose pin-access phase must reach the `ANTENNA_clkbuf_*` diodes already
   placed by the post-GRT diode repair, and 2 sit on clock nets with no access point.
   Jumper-only does NOT help — the crash is the re-route re-checking pre-existing
   diodes, not the jumper insertion (confirmed crashing twice: the Metal4 run and
   `RUN_2026-06-13_18-04-16`). The 1 residual is non-gating on gf180 (Magic DRC
   authoritative, KLayout antenna check disabled); literal-0 would need CTS/placement
   surgery, not repair tuning.
8. **Timing**: `CLOCK_PERIOD: 75` ns (~13.3 MHz) for the 11-macro variant. The 3-macro
   variant closed at **60 ns** (critical path = PE-array MAC). Making A/B SRAM puts the
   SRAM READ on the combinational MAC path: at the slow corner (ss_125C; SRAM is a 3V IP)
   the read alone is ~13 ns clk-to-Q, and high-fanout SRAM data nets span the spread-out
   macros, so the SRAM→mux→PE-MAC→accumulator path overran 60 ns by ~5.9 ns. 75 ns closes
   all 9 corners. To recover speed: pipeline/register the SRAM read, or cluster A/B macros
   near the PE array. The SRAM `lib` is registered per corner (tt/ss_125C/ff_n40C) so it is
   not black-boxed in multi-corner STA.

### Antenna closure study (Stage 1, 2026-06-13 → 06-14) — full iteration log

**Context.** The 11-macro DLA hardened clean on everything *except* GF180 **Metal2
*side-area* antenna** violations (plasma-induced gate-oxide damage risk during
fabrication; a per-net, per-layer metal-area-to-gate ratio — purely a fab/yield
concern, no runtime effect). In this open flow antennas are **non-gating** (Magic
DRC is the authoritative signoff; the KLayout antenna check is disabled), so even a
residual is manufacturable — but it was chased to literal 0 as a quality goal. The
residual at the grid baseline is a single long Metal2 signal net (`_03807_`, ratio
469/400 = **1.17×**, a high-fanout logic net, not an SRAM net).

**The DRT-0073 wall (why automated/targeted repair is unavailable here).** The
*targeted* fix for a Metal2 antenna is a **jumper** (hop the long run up a layer),
inserted by the in-detailed-route antenna repair. But **any `DRT_ANTENNA_REPAIR_ITERS
≥ 1` triggers a verification re-route whose pin-access phase cannot reach certain
clock-tree cells / antenna-diode cells → `[ERROR DRT-0073] No access point`**, which
aborts routing. Confirmed dead across five configs: padding 1 (diode mode), padding 1
(Metal4 cap), padding 3 (jumper-only), and **all-jumper with
`GRT_ANTENNA_REPAIR_JUMPER_ONLY: true`** (zero repair-inserted diodes) — the last
still crashed because the ~8,900 diodes from `RUN_HEURISTIC_DIODE_INSERTION` (not the
repair) include clock-net diodes the re-route can't reach. More cell padding only
*shuffles which cell* fails. And the residual net already carries **5 antenna diodes**
yet still violates → it is a wire-*length* problem, so more diodes
(`GRT_ANTENNA_REPAIR_MARGIN`↑) is futile too. Net: no in-flow tool can targetedly fix
it, so closure was pursued via floorplan/placement.

**Iteration log.** (All runs 11 macros; `CLOCK_PERIOD 75 ns` and
`DRT_ANTENNA_REPAIR_ITERS 0` unless noted. Magic DRC = 0 and LVS = 0 on every run that
completed. "ws" = worst-corner setup slack.)

**Resolution.** The targeted levers were dead and every *large* floorplan move
(clustering, density-70, max-fanout, row-swaps) *worsened* the count (3–6) — evidence
the channel-fragmented grid sits near a local antenna optimum. Closure came from a
**deterministic placement-perturbation sweep** off that grid: macro-position swaps
re-rolled the antenna set (3/5/3, all worse), but a one-point `PL_TARGET_DENSITY_PCT
55→56` nudge re-routed the lone net clean → **0 net / 0 pin**, DRC 0, LVS 0, all 9
corners closed (setup +7.58 ns, hold +0.22 ns). Re-running the promoted `config.yaml`
gave a **byte-identical GDS (18,985,336 B)** with 0 antennas → deterministic and
reproducible, not a routing-thread fluke. Deliverable GDS: `runs/confirm_d56` (≡
`runs/b_density56`)`/final/gds/dla_engine_top.gds`. `config.yaml` is promoted to
density 56 and reproduces it.

**Lessons / findings (for the report).**
1. For a *marginal* single-net antenna (~1.1×), a **tiny deterministic placement
   perturbation** (density ±1, or a macro swap) is a valid closure lever: it re-rolls
   which nets route long, and because the flow is deterministic a found 0 reproduces.
2. **Large floorplan changes reshuffle antennas and tend to *worsen* them** here
   (clustering 1→4; row-swaps 3–5) — they spread the logic and spawn new long buffer
   nets. Counter-intuitively, the compact channel-fragmented grid is the sweet spot.
3. **Timing ↔ antenna trade-off:** floorplans that shorten the SRAM→MAC critical path
   (clustering, A↔B swap → setup ~+14.7 ns vs +7.6 ns, i.e. ≈62 ns clock feasible)
   consistently *cost* antennas (3–4). A future speed pass can exploit this if the
   antenna target is relaxed.
4. **gf180 antenna checks are non-gating** in this flow → even the 1-net baseline is a
   valid tapeout; literal 0 was a quality goal, not a signoff requirement.

### Voltage domains & the planned SRAM swap

gf180mcu is a multi-voltage 180 nm process, but the open PDK ships **only 5 V** digital
standard cells (`gf180mcu_fd_sc_mcu7t5v0`/`9t5v0`) — there is **no 3.3 V std-cell
library**, so the logic cannot be made 3.3 V. The current design is therefore
mixed-domain: **5 V logic + 3.3 V SRAM** (`gf180mcu_ocd_ip_sram__sram256x8m8wm1`,
`nom_voltage 3.3`). This is fine for the layout (DRC/LVS clean) but needs level
shifting / a separate rail for real silicon.

**Plan to make it single-supply (5 V):** swap the SRAM to the 5 V
`gf180mcu_fd_ip_sram__sram256x8m8wm1` (same 256×8; the 5 V `fd` family exists in the
PDK and is used by the `librelane_rtl2gds_gf180` example 02). The swap is contained —
only the cell name in the `gf180_sram_1rw_256x8.v` wrapper + the `MACROS:` block in
`config.yaml` change; the rest of the design and all the fixes above carry over.
Re-verify the 5 V SRAM's power-pin layers (the Metal3 PDN connect is ocd-specific) and
physical size. **Do this swap before any padring/chip-top (Stage 2) integration**, since
that step consumes the hardened macro GDS.
